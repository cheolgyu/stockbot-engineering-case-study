# 역사적 시스템 아키텍처

아래 구조는 2022~2025년 주 Rust 구현을 설명합니다. 현재 운영 중이라는 의미가 아니며, 2026년 React·Axum 현대화 상태와도 구분합니다.

```mermaid
flowchart LR
    Source[외부 시장 데이터] --> Scheduler[스케줄 진입점]
    Scheduler --> Batch[Batch]
    Batch --> Job[Job]
    Job --> Step[Step]
    Step --> DB[(PostgreSQL)]
    DB --> API[Actix Web + SQLx API]
    API --> Web[Yew + WebAssembly]
```

## 계층별 책임

### 수집·배치

- 일정 실행을 업무 단위에서 분리했습니다.
- `Batch`, `Job`, `Step` 인터페이스로 큰 작업을 순차 단계로 조합했습니다.
- PostgreSQL 함수와 쿼리를 이용해 일별 데이터를 주간 단위로 집계했습니다.
- 배포·백업 자동화도 시도했지만, 이 사례집은 운영 식별자와 환경 설정을 공개하지 않습니다.

이 구조는 Spring Batch의 용어와 수명주기에서 착안한 자체 구현입니다. Spring Batch 자체를 Rust로 완전히 재구현했다는 주장은 아닙니다.

### API

확인된 역사적 manifest는 Actix Web, SQLx, PostgreSQL, OpenAPI 도구 사용을 보여줍니다. API 계층은 집계 데이터를 웹 클라이언트가 소비할 수 있는 형태로 전달했습니다.

원본 검토에서는 오류 처리와 경계 설정을 더 다듬어야 할 지점도 확인됐습니다. 이 저장소는 원본 코드를 복사해 완성품처럼 제시하지 않고, 아키텍처 사실과 품질 주장을 분리합니다.

### 웹

역사적 웹 클라이언트는 Yew, `wasm-bindgen`, `gloo`, `yew-router`를 사용한 Rust/WASM 애플리케이션이었습니다. 2026년에는 React로 전환하는 현대화가 진행됐습니다.

이 선택은 “한 언어로 전 계층을 통일하는 것” 자체보다 제품 개발 속도와 라이브러리 적합성이 중요할 때 기술 선택을 바꿀 수 있다는 사례입니다.

## Rust 선택의 실제 근거

Rust를 학습하고 적용한 동기는 다음과 같습니다.

- 배치·API·당시 WASM 클라이언트에서 하나의 타입 시스템을 사용하려는 시도
- 장시간 실행되는 작업에서 런타임과 메모리를 세밀하게 통제하려는 목표
- ARM64를 포함한 단일 실행 파일 배포 실험
- 소유권과 오류 타입으로 경계 조건을 더 명시적으로 만들려는 목적

이는 설계 동기입니다. Go·Spring·Rust 버전을 동일 데이터와 장비로 비교한 벤치마크가 없으므로 실제 속도·메모리 개선 수치로 바꾸어 말하지 않습니다.

## 공개 재구성의 범위

이 저장소에는 전체 수집기나 API를 재현하지 않습니다. 채용 검토에서 설명력이 높고 외부 의존성이 작은 두 부분만 실행 가능하게 만들었습니다.

1. 실패 수명주기가 명확한 Rust 배치 실행 모델
2. ISO 주차 경계를 검증하는 PostgreSQL 집계

이 범위를 좁힌 이유는 작은 예제를 큰 시스템인 것처럼 보이게 하려는 것이 아니라, 비공개 원본을 유출하지 않고도 실제 설계 판단과 개선 능력을 검증할 수 있게 하기 위해서입니다.
