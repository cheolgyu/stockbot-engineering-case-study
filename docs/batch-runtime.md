# 배치 실행 모델과 실패 처리

## 원래 의도

데이터 수집과 집계를 한 함수에 몰아넣지 않고 다음 세 수준으로 나눴습니다.

- `Batch`: 한 번의 전체 실행과 정책
- `Job`: 업무상 묶이는 단계의 집합
- `Step`: 실제 부작용을 수행하는 최소 실행 단위

이 추상화는 여러 작업의 순서를 읽기 쉽게 만들고, 공통 전후 처리를 한곳에 모으기 위한 것이었습니다.

## 소스 검토에서 발견한 결함

역사적 구현은 성공 경로에서는 전후 처리를 호출했지만, 오류가 중간에 반환되면 일부 `run_after`와 실패 상태 기록을 건너뛸 수 있었습니다. `unwrap`과 `expect`도 남아 있어 실패를 구조화된 실행 결과로 전달하지 못하는 경로가 있었습니다.

이 결함 때문에 원본 코드를 “완성된 프레임워크”라고 공개하지 않았습니다. 대신 실패 의미를 먼저 정한 뒤 작은 독립 예제로 다시 작성했습니다.

## 공개 예제의 계약

[`examples/resilient-batch`](../examples/resilient-batch/)는 외부 crate가 없는 순수 Rust 예제입니다.

```text
Batch Started
  Job Started
    Step Started
    Step Finished(Succeeded | Failed)
  Job Finished(Succeeded | Failed)
Batch Finished(Succeeded | Failed)
```

실행 규칙은 다음과 같습니다.

1. `Step::run`이 panic 없이 `Result`를 반환한 경로에서는 시작된 모든 범위가 하나의 `Finished` 이벤트를 남깁니다.
2. 단계 실패는 단계, 소속 작업, 배치까지 실패로 종결합니다.
3. 현재 정책은 fail-fast이며 실패 뒤의 단계와 작업은 실행하지 않습니다.
4. 오류에는 실패한 작업명·단계명·원인 메시지가 보존됩니다.
5. 빈 작업이나 빈 배치도 명시적으로 성공 종료합니다.

## 의도적으로 하지 않은 것

- 재시도, skip, partition, 병렬 실행을 구현하지 않았습니다.
- panic 복구와 hang timeout을 구현하지 않았습니다.
- 이벤트의 영속 저장소를 특정 DB에 결합하지 않았습니다.
- Exactly-once 실행을 주장하지 않습니다.
- 이 예제를 원본 프로덕션 코드라고 주장하지 않습니다.

실제 시스템으로 확장한다면 실행 리포트를 같은 DB transaction에서 저장할지, 업무 데이터와 별도 outbox로 남길지 먼저 결정해야 합니다. 이 사례집은 작은 코드에서 검증할 수 있는 실패 수명주기에 초점을 맞춥니다.
